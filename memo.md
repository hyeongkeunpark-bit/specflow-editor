  3. 유사 서비스 리서치 — 비표준 사용성 패턴
                                                                                             
  가장 참고할만한 패턴 (우선순위순)
                                                                                             
  1. 하이라이트-투-에딧 (ChatGPT Canvas)                                                     
                                                                                             
  - Spec 패널에서 텍스트를 드래그 선택 → 선택 영역이 채팅에 인용되어 "이 부분을 수정해줘"    
  컨텍스트가 자동 전달                                            
  - 현재 SpecFlow와의 갭: Spec 패널이 read-only ReactMarkdown. 텍스트 선택 이벤트를 잡아서   
  채팅에 넘기는 로직 없음                                                                    
  
  2. 프리뷰 요소 직접 참조 (Lovable)                                                         
                                                                  
  - 프로토타입 프리뷰에서 UI 요소를 클릭 → 채팅에서 해당 요소를 참조하여 수정 지시           
  - 현재 SpecFlow와의 갭: iframe sandbox로 인해 부모↔자식 통신 불가. postMessage 브릿지 필요
                                                                                             
  3. 비파괴적 되돌리기 (Lovable)                                  
                                                                                             
  - 버전 복원 시 이후 스냅샷을 삭제하지 않고, 새 스냅샷으로 "되돌림" 기록을 생성             
  - 현재 SpecFlow 동작: handleRestore가 snapshots.slice(0, index + 1)로 이후를 영구 삭제
                                                                                             
  4. 변경 사항 시각적 표시 (ChatGPT Canvas / Cursor)                                         
                                                                                             
  - AI가 수정한 부분을 diff 하이라이트로 표시. Accept/Reject 가능                            
  - 현재 SpecFlow: generateChangeSummary로 "어떤 섹션이 변경됐는지" 텍스트 요약만 제공
                                                                                             
  5. 버전 분기(Forking) (Claude Artifacts)                                                   
                                                                                             
  - 이전 프롬프트를 수정하면 해당 시점에서 히스토리가 트리 구조로 분기                       
  - 현재 SpecFlow: 선형 히스토리만 지원                           
                                                                                             
  6. AutoFix 후처리 (v0.dev)                                                                 
  
  - 생성된 HTML/코드에서 에러를 자동 스캔 → 수정 제안                                        
  - 현재 SpecFlow: 프로토타입 HTML 에러 감지 없음                 
                                                                                             
  7. 안정 버전 마킹 (Lovable)                                                                
                                                                                             
  - 특정 버전에 "즐겨찾기" 표시 → 되돌리기 시 안전한 기준점                                  
  - 현재 SpecFlow: 모든 스냅샷이 동등한 레벨                      
                                                                                             
  8. Graceful Degradation — AI 실패 시 수동 편집 전환                                        
                                                                                             
  - AI 응답 실패/타임아웃 시 Spec 패널을 직접 편집 가능한 에디터로 전환                      
  - 현재 SpecFlow: AI 실패 시 에러 메시지만 표시. 수동 편집 불가

      </button>

  <div class="container"><h1 class="title">안녕하세요</h1><button class="btn">확인</button></div>

  2. Fuzzy 매칭                                                                                                                                                                       
                                                                  
  현재: Claude가 변경 부분만 출력 (delta 방식)
  <search>    .btn { color: #333; }</search>    ← AI가 출력한 검색어
  <replace>   .btn { color: #000; }</replace>                                                                                                                                         
  기존 HTML에서 이 텍스트를 찾아서 교체하려는데, 공백이 2칸 vs 4칸 같은 사소한 차이로 "못 찾겠음" → 실패                                                                              
                                                                                                                                                                                      
  Fuzzy: 각 줄의 앞뒤 공백을 무시하고 비교                                                                                                                                            
  AI: ".btn { color: #333; }"  (공백 제거 후)                                                                                                                                         
  HTML: ".btn { color: #333; }" (공백 제거 후)                                                                                                                                        
  → 같음! 매칭 성공                                                                                                                                                                   
                                                                  
  원리: 매칭 실패의 대부분 원인(들여쓰기 차이)을 보정 → delta 성공률 상승. 단, 구조적으로 다른 변경(라이브러리 추가 등)에는 여전히 실패.

  messages: messages.map((m, i) => {                                                                                                                                                    
    if (i === messages.length - 2 && ...) {                                                                                                                                             
      return { ..., cache_control: { type: "ephemeral" } };                                                                                                                             
    }                                                                                                                                                                                   
    return { role, content: m.content };                          
  })                                                                                                                                                                                    
                                                                  
  // 개선: 최상위 자동 캐싱
  const stream = anthropic.messages.stream({
    model: MODEL,                                                                                                                                                                       
    max_tokens: 16384,
    thinking: { type: "adaptive", display: "omitted" },                                                                                                                                 
    cache_control: { type: "ephemeral" },  // 최상위에 한 줄

    messages: messages.map(m => ({  // breakpoint 로직 제거

## 1. 스트리밍 취소 시 raw `<prototype_delta>` 텍스트 노출 (우선순위: 중, 난이도: 낮음)

### 원인
`Index.tsx:283-285` 취소 처리 로직:
```ts
if (err instanceof DOMException && err.name === "AbortError") {
  const partial = rawStreamRef.current.trim();  // ← raw 그대로 사용
  setMessages(...{ ...m, content: partial || "응답 시간이 초과되었습니다..." });

```
스트리밍 중에는 `stripStreamingNoise`로 "(Prototype 수정 중...)"로 치환되지만, 취소 시에는 `rawStreamRef.current`를 그대로 씀.

### 수정 방향
취소 시에도 partial을 정제. delta/HTML/spec 태그 시작 지점까지만 남기고 뒤를 잘라냄:
```ts
if (err instanceof DOMException && err.name === "AbortError") {
  const partial = rawStreamRef.current;
  const cutPoints = [
    partial.indexOf("<prototype_delta>"),
    partial.indexOf("<spec>"),
    partial.indexOf("```html"),
    partial.search(/<!DOCTYPE html/i),
  ].filter((i) => i >= 0);
  const clean = cutPoints.length > 0
    ? partial.slice(0, Math.min(...cutPoints)).trim()
    : partial.trim();
  const display = clean || "(응답 중단됨)";
  setMessages(...{ ...m, content: display });
}
```

현재 파싱 로직이 thinking 블록을 완벽히 스트립하지 못하고 delta search 내부로 새어들어감.

관련 코드: `src/lib/parser.ts` + `src/lib/api.ts`의 `extractDeltaPairs`

### 조사 필요 사항
1. `server.ts`에서 Extended Thinking이 활성화되어 있는지 확인 (`thinking: {...}` 옵션)
2. 8971c03 커밋 ("thinking 제거")에서 어떻게 처리했는지 확인
3. `parseResponse` / `extractDeltaPairs`의 입력에 thinking 태그 남아있는지

### 수정 방향
- 옵션 A: 서버에서 thinking 블록을 아예 응답에서 제거 (`anthropic.messages.stream`의 응답 이벤트에서 thinking content type 필터링)
- 옵션 B: 클라이언트 파싱 전에 `<thinking>...</thinking>` 스트립 추가
- 옵션 C: extractDeltaPairs에서 thinking 태그가 섞인 delta search는 invalid로 판정하고 Morph로 바로 회부

### 영향 범위
- `server.ts`의 스트리밍 핸들링 or `src/lib/parser.ts`의 파싱
- Morph 폴백이 어차피 받아주고 있어서 실제 유저 영향은 미미 (latency 조금 증가)

### 예상 작업량
1-2시간 (조사 + 수정 + 테스트)

## 4. 🚨 시스템 프롬프트 구조 개선 — composable chunks (우선순위: 낮음, 장기, **불안정한 개선**)

> ⚠ **불안정한 개선**: 이득은 간접적이고, 리스크(AI 품질 회귀)는 직접적. 
> E2E 인프라(항목 5) + 품질 벤치마크 갖춰지기 전까지 **착수 금지**.

### 배경
현재 시스템 프롬프트(`prompt-v4-prototype-first.md`, 18389자)가 **모놀리식**. 특정 규칙 하나 수정하면 다른 기능에 영향 줄 수 있다는 불안.

일부는 이미 격리됨:
- `/api/chat/fix-errors`: 전용 짧은 프롬프트
- 일관성 검토, Use Case 분석: `systemPromptMode: "none"` + 하드코딩 instruction

### 개선 방향
**composable prompt chunks**:
- 공통 규칙(delta 출력 형식, Spec 구조 등) → 재사용 chunk
- 작업 전용 규칙(Prototype-first 플로우, 에러 수정 등) → 별도 chunk
- 호출 시 필요한 chunk만 조합
- TypeScript 상수 파일로 관리하면 타입 안전성 + DRY

예시 구조:
```ts
// src/lib/prompts/chunks.ts
export const DELTA_OUTPUT_RULES = `...`;
export const SPEC_STRUCTURE_RULES = `...`;
export const PROTOTYPE_FIRST_WORKFLOW = `...`;

// src/lib/prompts/compose.ts
export function composePrompt(type: "chat" | "fix-errors" | "consistency") {
  switch(type) {
    case "chat": return [DELTA_OUTPUT_RULES, SPEC_STRUCTURE_RULES, PROTOTYPE_FIRST_WORKFLOW].join("\n\n");
    ...
  }
}
```

### 🔴 왜 "불안정한 개선"인가
- 18389자 모놀리식 프롬프트는 **섹션 간 상호 참조** 가능성 → 기계적 분해 후 단순 concat 재조합이 원본과 **동일한 모델 behavior 보증 불가**
- AI 품질 미세 변화 (예: delta 성공률 89% → 80%)를 즉시 탐지할 수단 없음
- **측정 불가 → 품질 회귀 전파 위험**
- 이득(토큰 1500-3000/call 절감, 수정 안전성)은 간접적/정성적
- 리스크(AI 품질 하락)는 직접적/유저 영향

### 선결 과제 (반드시 먼저)
1. **E2E 테스트 인프라** (항목 5) — 회귀 탐지 기반
2. **delta 성공률 벤치마크** — 프롬프트 변경 전후 품질 지표 비교
3. 위 두 개 없으면 "바뀌었는지, 얼마나 나빠졌는지" 알 수 없음 → 착수 금지

### 영향 범위
- 대규모 리팩터링
- `prompt-v4-prototype-first.md` 분해 → 여러 `.ts` chunk
- `server.ts`의 `loadSystemPrompt()` 교체
- 라이브 품질 회귀 가능 (AI 작문 변화)

### 예상 작업량
- 구현: 2-3일
- 회귀 검증: 2-3일 (E2E + 벤치마크 선행 필요)
- **합계: 4-6일** (선결 과제 포함 시 1-2주)

## 6. 🚨 Tool use 아키텍처 전환 (우선순위: 낮음, 장기, **불안정한 개선**)

> ⚠ **불안정한 개선**: 현재 시스템이 안정적으로 돌아가고 있음 (delta 89% + Morph 폴백으로 전체 100% 성공률).
> 이 전환은 **절박할 때만** 착수. 그냥 "좋아 보여서" 진행 금지.

### 배경
AI가 `<prototype_delta>` / `<spec>` XML 태그로 출력 → 정규식 파싱 → 적용하는 구조를 **tool_use 기반**으로 전환:
- AI가 `apply_prototype_delta({search, replace})` tool 호출
- 서버가 tool_use 블록 받아 처리
- tool_result로 성공/실패 반환 (AI가 같은 턴에서 재시도 가능)

### 이득 (정량)
- **delta 파싱 실패율 ≈ 0%** (JSON schema 강제)
  - 현재 관찰된 파싱 실패: `</thinking>` 태그 누설, 태그 불일치, 이스케이프 문제
  - 모두 소멸. search 불일치만 남음 (AI 작문 문제)
- **출력 토큰 15-25% 절감** (XML 오버헤드 ~80자/delta → JSON ~28자/delta)
- 월 수만 호출 기준 **$10-30/월** 절감

### 유저 관점
- 긍정: 수정 실패 빈도 감소 체감, 응답 latency 미세 개선
- 부정: 스트리밍 중 "(Prototype 수정 중...)" 같은 실시간 피드백 **약화** (tool_use JSON은 부분 표시 어려움)

### 🔴 왜 "불안정한 개선"인가

**100% 안전 영역**:
- Prototype 수정 일반 플로우
- Spec 업데이트 버튼 (specUpdateMode)
- Prototype 업데이트 버튼 (protoUpdateMode)
- Use Case 분석 / Spec 일관성 검토
- 에러 자동 수정 + dedup
- 파일 업로드 / 이미지 첨부 / R2 공유 / 세션 CRUD
- 캐시 (system prompt)

**⚠ 주의 필요 영역**:
- Spec 수정 (마크다운 구조 복잡, tool schema 설계 섬세히)
- 폴백 체인 재설계 (파싱 실패 개념 소멸)
- 스트리밍 UX (JSON은 실시간 표시 약함)
- Extended thinking 조합 (이벤트 순서 재검증)
- 취소 / AbortController

**🔴 최대 리스크 — 대화 이력 호환성**:
- 기존 세션 이력에 `<prototype_delta>` text 응답 남아있음
- 전환 후 Anthropic에게 이건 **text**로 보임 (tool_use 아님)
- 모델이 혼란 가능 ("이전엔 XML로 했는데?")
- 해결: (a) 새 세션만 tool_use 사용 / (b) 기존 이력 마이그레이션 (복잡)

### 선결 과제 (반드시 먼저)
1. **E2E 테스트 인프라** (항목 5) — 전환 후 회귀 탐지용
2. **현재 delta 성공률 벤치마크** — 전환 전/후 비교 기준점
3. **마이그레이션 전략 결정** — 새 세션만 vs 전환
4. 기존 유닛 테스트 44개는 `<prototype_delta>` 기반 → **대부분 재작성 필요**

### 영향 범위
- `parser.ts`, `api.ts`, `server.ts`, `Index.tsx` — 주요 수정
- 프롬프트 수정 (tool 사용 유도)
- 유닛 테스트 대부분 재작성
- 라이브 데이터 마이그레이션 고려

### 예상 작업량
- 설계 (tool schema, migration 전략): 2-3일
- 구현: 1주
- 테스트 재작성: 3-5일
- E2E 회귀 테스트: 3-5일
- 라이브 안정화: 1주
- **합계: 3-4주**

### 착수 판단 기준
다음 중 **하나라도 해당**하면 고려:
- 파싱 실패율이 10% 이상 지속
- 유저가 "AI가 이상하게 수정한다" 신고 빈번
- 토큰 비용이 임계치 초과
- tool_use fine-tuning된 새 모델 출시로 품질 격차 커짐

위 신호 없이는 **착수 금지**. 현재 상태(delta 89% + fallback)가 실용적으로 충분.

## 5. E2E 테스트 인프라 (Playwright/Cypress) 도입 (우선순위: 중-높, 난이도: 중)

### 배경
이번 QA에서 자동화 불가능했던 시나리오들:
- 4-5 세션 전환 state 격리
- 4-6 히스토리 v{N} 복원
- 4-8 스트리밍 취소 UI
- 4-9 localStorage 복원
- 5-1~5-4, 5-7, 5-10 버튼 UI 플로우

전부 **브라우저 자동화**가 필요한 시나리오. 현재 유닛 테스트(Vitest 44개)로는 커버 불가.

### 도입 방향

**Playwright 권장 이유**:
- TypeScript 지원 훌륭
- iframe 제어 가능 (SpecFlow의 iframe 에러 캡처 테스트 가능)
- 네트워크 인터셉트 (API 모킹 가능, 또는 실 서버 테스트)
- 멀티 브라우저 (Chrome/FF/Safari) 지원
- 병렬 실행 속도 빠름

### 최소 시나리오 (MVP)

**Phase 1 — AI 호출 없는 3개 (인프라 작동 확인 먼저)**
1. `session-crud.spec.ts` — 세션 생성/전환/삭제 (4-5, 5-10) — localStorage/상태만 검증
2. `reload-restore.spec.ts` — 새로고침 후 세션 복원 (4-9) — 동일
3. `file-upload.spec.ts` — Spec/HTML 파일 업로드 자동 로드 (5-9) — 파일 → state 반영

**Phase 2 — fixture 설계 필요한 2개 (Phase 1 안정화 후)**
4. `restore-flow.spec.ts` — 히스토리 복원 후 state 보존 (4-6, 4-7 auto-patch, S-lite)
5. `cancel-streaming.spec.ts` — 스트리밍 중 취소 (4-8)

### AI 호출 방침 (중요)
"AI 호출은 모킹" 단순 대응은 부족. `/api/chat` 응답 파싱이 SpecFlow 핵심 로직이라 전부 모킹하면 reducer/parser/delta 로직을 우회 → 회귀 탐지력이 떨어짐.

**레이어 분리 원칙**:
- **UI/상태 레이어 (E2E)** — 고정 fake response fixture로 모킹. session-crud / reload-restore / file-upload / cancel-streaming / restore-flow의 UI·state·히스토리 검증에 집중
- **AI 품질 레이어** — `test-delta.ts`에서 실 API 호출로 커버 (이미 존재). delta 성공률·파싱 회귀는 여기서

즉 E2E는 "AI 품질까지 다 본다"는 욕심을 버리고 UI 상태·세션·복원·스트리밍 취소 커버에 집중. 중복 안 되게 역할 분담.

### 설치 방법
```
# @playwright/test ^1.57.0 devDep에 이미 있음 — 추가 설치 불필요
npx playwright install chromium   # 브라우저 바이너리만 설치
```

### 기존 `playwright.config.ts` 상태 (주의 — memo 오기 정정)
프로젝트에 파일은 있지만 **Lovable 템플릿 stub**이라 실행 불가:
- `playwright.config.ts` → `lovable-agent-playwright-config`에서 `createLovableConfig` re-export
- `playwright-fixture.ts` → 동일 패키지에서 `test, expect` re-export
- **해당 패키지는 package.json·node_modules 어디에도 없음** → 현 상태로 `npx playwright test` 실행 시 `ERR_MODULE_NOT_FOUND`
- `lovable-tagger` (vite plugin, UI 컴포넌트 태깅용)와는 무관한 파일이므로 **활성 자동화 대상 아님**

**조치**: stub 2개 삭제 후 새 `playwright.config.ts` 작성. Lovable 기능(vite-tagger) 영향 없음.

### 가치
- 이번 배포에서 수동 3시간+ 걸린 QA를 **5-10분 자동 실행**으로 축소

- 배포 CI 통합 가능 (Vercel 프리뷰 URL에서 E2E 자동 실행)

### 영향 범위
- `e2e/` 디렉토리 신규 (vitest `include` 패턴과 분리 필수 — `src/test/*.test.ts`만 잡도록 확인)

- `package.json`에 `test:e2e` 스크립트 추가
- CI 파이프라인 통합은 **제외** (로컬 실행만 — Vercel preview E2E는 실 API 비용·rate limit 리스크)
