  3. 유사 서비스 리서치 — 비표준 사용성 패턴
                                                                                             
  가장 참고할만한 패턴 (우선순위순)
                                                                                             
  1. 하이라이트-투-에딧 (ChatGPT Canvas)                                                     
                                                                                             
  - Spec 패널에서 텍스트를 드래그 선택 → 선택 영역이 채팅에 인용되어 "이 부분을 수정해줘"    
  컨텍스트가 자동 전달                                            
  - 현재 SpecFlow와의 갭: Spec 패널이 read-only ReactMarkdown. 텍스트 선택 이벤트를 잡아서   
  채팅에 넘기는 로직 없음                                                                    
  
  2. 프리뷰 요소 직접 참조 (Lovable)                                                         
                                                                  
  - 프로토타입 프리뷰에서 UI 요소를 클릭 → 채팅에서 해당 요소를 참조하여 수정 지시           
  - 현재 SpecFlow와의 갭: iframe sandbox로 인해 부모↔자식 통신 불가. postMessage 브릿지 필요
                                                                                             
  3. 비파괴적 되돌리기 (Lovable)                                  
                                                                                             
  - 버전 복원 시 이후 스냅샷을 삭제하지 않고, 새 스냅샷으로 "되돌림" 기록을 생성             
  - 현재 SpecFlow 동작: handleRestore가 snapshots.slice(0, index + 1)로 이후를 영구 삭제
                                                                                             
  4. 변경 사항 시각적 표시 (ChatGPT Canvas / Cursor)                                         
                                                                                             
  - AI가 수정한 부분을 diff 하이라이트로 표시. Accept/Reject 가능                            
  - 현재 SpecFlow: generateChangeSummary로 "어떤 섹션이 변경됐는지" 텍스트 요약만 제공
                                                                                             
  5. 버전 분기(Forking) (Claude Artifacts)                                                   
                                                                                             
  - 이전 프롬프트를 수정하면 해당 시점에서 히스토리가 트리 구조로 분기                       
  - 현재 SpecFlow: 선형 히스토리만 지원                           
                                                                                             
  6. AutoFix 후처리 (v0.dev)                                                                 
  
  - 생성된 HTML/코드에서 에러를 자동 스캔 → 수정 제안                                        
  - 현재 SpecFlow: 프로토타입 HTML 에러 감지 없음                 
                                                                                             
  7. 안정 버전 마킹 (Lovable)                                                                
                                                                                             
  - 특정 버전에 "즐겨찾기" 표시 → 되돌리기 시 안전한 기준점                                  
  - 현재 SpecFlow: 모든 스냅샷이 동등한 레벨                      
                                                                                             
  8. Graceful Degradation — AI 실패 시 수동 편집 전환                                        
                                                                                             
  - AI 응답 실패/타임아웃 시 Spec 패널을 직접 편집 가능한 에디터로 전환                      
  - 현재 SpecFlow: AI 실패 시 에러 메시지만 표시. 수동 편집 불가

  ## 구현 완료 (커밋 5190d95)

  ### 1. iframe 에러 캡처 시스템 — src/lib/iframeErrors.ts (신규)
  왜: AI에게 "ReferenceError: addTodo is not defined" 같은 실제 에러를 알려주기 위해.
  구현:
  - injectErrorCapture() — HTML의 <head> 직후에 에러 캡처 <script> 주입
  - window.onerror로 런타임 에러 캡처 (최대 5개, 폭주 방지)
  - window.addEventListener("unhandledrejection")로 Promise 에러 캡처
  - load 시 인라인 핸들러 정적 검증: onclick="X()" → window.X 존재 여부 체크 → 클릭 전에 에러 발견
  - sandbox 관련 SecurityError(localStorage 등) 필터링 (__skip 함수)
  - parent.postMessage로 부모 프레임에 에러 전달
  결과: 에러 배지("2 errors")와 자동 수정 버튼이 Prototype Preview 헤더에 표시됨.

  ### 2. 클라이언트 직접 패치 — src/lib/iframeErrors.ts의 tryClientPatch()
  왜: AI가 delta search를 틀리게 써서 에러를 못 고치므로, AI 없이 직접 고치는 게 100% 안정적.
  지원 패턴:
  - patchUndefinedSymbol(): "X is not defined" + X가 클래스 메서드 + 인스턴스 변수 찾음
    → 인라인 핸들러에서 onclick="X()" → onclick="인스턴스.X()" 치환
    → 실제 테스트: onclick="addTodo()" → onclick="app.addTodo()" ✅ (4글자 추가, 나머지 100% 유지)
  - patchWrongMethodName(): "X is not a function" + 유사 메서드 찾음
    → this.X() → this.유사메서드() 치환
    → 실제 테스트: this.renderTodos() → this.render() ✅
  동작 방식: 자동 수정 버튼 클릭 → tryClientPatch() 먼저 시도 → 성공하면 즉시 HTML 업데이트, AI 호출 0.

  ## 현재 핵심 미해결 문제 — delta 매칭

  ### 문제

  AI가 prototype 수정 시 <prototype_delta> 형식으로 응답함:
  ```
  <prototype_delta>
  <search>기존 HTML에서 변경할 부분 (원문 그대로)</search>
  <replace>변경 후 내용</replace>
  </prototype_delta>
  ```
  문제: AI가 <search> 안에 **원본 HTML의 원문을 정확히 재현하지 못함**.

  실제 실패 사례 (콘솔 로그에서 확인):
  ```
  [SpecFlow] applyPrototypeDeltas FAIL
  search: <button onclick="addTodo()">할일 등록</button>
  원본_근처: <button onclick="addTodo()" style="padding:15px 25px;background:#ff7f00;...
  method: exact+fuzzy+normalized 모두 실패
  ```
  → AI가 style 속성을 누락. 원본에는 긴 style이 있는데 AI가 기억으로 축약해서 씀.

  또 다른 실패:
  ```
  search: addTodo(){const todoText=document.getElementById('todo-input').value.trim();...
  원본_근처: (키워드 없음)
  ```
  → AI가 원본에 없는 코드를 상상해서 씀. 실제 원본은 다른 변수명, 다른 구조.

  ### 왜 발생하는가

  1. 프로토타입 HTML이 minified 상태 (토큰 절감 목적) → 한 줄에 수천 글자 → AI가 정확히 복사 못 함
  2. AI는 코드를 "읽고 기억"하는 게 아니라 "의미를 이해하고 재구성"함 → 재구성할 때 세부 차이 발생
  3. 시스템 프롬프트에 "현재 HTML의 원문 그대로" 규칙이 있지만, AI가 완벽히 따르지 못함

  ### 현재 폴백 체인과 각 단계의 문제

  1. exact delta match → 실패 (search 텍스트가 원본과 다름)
  2. fuzzy match (줄 단위 trim 비교) → 실패 (원본이 minified라 줄 단위가 무의미)
  3. normalized match (CSS 값 유연 비교) → 실패 (CSS가 아니라 코드 구조 자체가 다름)
  4. Morph API → 실패 (delta에서 추출한 search/replace가 부정확하니 Morph도 맥락 못 잡음)
  5. Claude 전체 HTML 재출력 요청 → "기능 삭제" 발생 (대화이력 오염 + AI가 축약해서 재출력)

  ### 웹 Claude 채팅과의 비교

  웹 Claude 채팅에서는 같은 수정을 잘 해냄.
  차이: 웹 Claude는 **전체 HTML을 처음부터 끝까지 출력**함. delta(search/replace) 형식을 안 씀.
  → 매칭 과정이 없으므로 실패할 수 없음.
  SpecFlow에서 delta를 쓰는 이유: 출력 토큰 ~60% 절감. 하지만 실패율이 높아 오히려 비용이 더 나올 수 있음.

  ## 시행착오 — 무엇을 시도했고 왜 실패했는가

  ### 시도 1: 에러 메시지를 AI에게 전달
  가설: AI가 에러를 모르니까 못 고치는 것. 에러를 알려주면 고칠 것.
  결과: AI가 에러를 받고도 "기능 삭제"로 해결. 또는 엉뚱한 곳을 수정.
  교훈: 에러 메시지만으로는 부족. 원인 분석(어디에 정의됨, 올바른 호출 방법)까지 필요.

  ### 시도 2: 프롬프트에 "기능 제거 금지" 규칙 추가
  가설: 규칙으로 AI 행동을 제어할 수 있을 것.
  결과: 일부 개선되나 100% 제어 불가. AI가 전체 HTML 재출력할 때 여전히 기능 빠뜨림.
  교훈: 프롬프트 제약은 보조 수단. 구조적 해결이 필요.

  ### 시도 3: 에러 수정 전용 엔드포인트 (대화이력 격리)
  가설: 대화이력에 "기능 제거해줘"가 있어서 오염되는 것. 격리하면 해결.
  결과: 대화이력 오염은 해결했지만, AI가 여전히 delta search를 틀리게 씀 → 매칭 실패 → 수정 적용 안 됨.
  교훈: 대화이력 오염과 delta 매칭 실패는 별개 문제. 둘 다 해결해야 함.

  ### 시도 4: 클라이언트 직접 패치
  가설: 흔한 에러 패턴은 AI 없이 regex로 고칠 수 있음.
  결과: ✅ 성공. onclick="addTodo()" → onclick="app.addTodo()" 즉시 치환. AI 호출 0, 100% 성공.
  교훈: 정형화된 에러는 규칙 기반 패치가 AI보다 안정적. AI는 비정형 문제에만 사용.

  ## 다음 세션에서 이어서 할 것

  ### 1. [높음] delta 성공률 데이터 수집
  현재 delta가 얼마나 성공/실패하는지 실제 데이터가 없음.

  이 데이터가 있어야 아래 선택지 중 어떤 방향이 비용 대비 효과적인지 판단 가능.

  ### 2. [높음] delta 성공률 개선 또는 대안 전략 결정
  선택지:
  (a) minify 포기 → prettified HTML 유지
      - AI가 search를 정확히 쓸 확률 높아짐
      - 토큰 비용 ~60% 증가
      - 검증: 동일한 수정 요청으로 minified vs prettified delta 성공률 비교
  (b) 줄번호 참조 방식
      - HTML 전달 시 줄번호를 붙여서 AI가 "L15-L20 수정" 식으로 참조
      - minified에서는 줄번호가 의미 없으므로 (a)와 함께 써야 함
  (c) delta 포기 → 항상 전체 HTML 출력
      - 웹 Claude와 동일 방식. 매칭 실패 자체가 불가능. 가장 안정적.
      - 토큰 비용 가장 높음. 응답 속도 느림.
      - 하지만 현재 실패 시 폴백(Morph + Claude 재요청)하면 어차피 비용이 비슷하거나 더 높을 수 있음.
  (d) 현재 하이브리드 유지 + 폴백 개선
      - 전체 HTML 폴백 요청을 격리된 맥락으로 (에러 수정 전용 엔드포인트처럼)
      - 이미 일부 구현됨. 하지만 AI가 전체 HTML 쓸 때 기능 빠뜨리는 근본 문제는 남음.

  결정 기준: 1번의 데이터로 "현재 delta 성공률이 X%"를 확인한 뒤,
  - 70% 이상이면 (a)+(d)로 개선
  - 30% 미만이면 (c)로 전환이 합리적
  - 사이면 (a)를 먼저 시도해보고 성공률 변화 확인
